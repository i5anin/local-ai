# Ресурсы: как делать всё самому

Этот документ — практичный гид по самостоятельному пути: от запуска локальной ИИ на RTX 3070 Ti до «цифрового двойника» и роста как разработчика. Каждый раздел учит не «получить готовое решение», а **находить ответ самому** — по первоисточникам, на английском, с воспроизводимым алгоритмом. Все ссылки проверены и актуальны на 2026 год.

---

## Где брать модели и как выбирать под видеопамять

Два источника: **Ollama** (модели упакованы, ставятся одной командой) и **HuggingFace** (склад исходных и GGUF-весов, тысячи репозиториев). Для старта на RTX 3070 Ti берите Ollama; HuggingFace нужен, когда модели в библиотеке Ollama нет или нужна конкретная квантизация.

### 1. Библиотека Ollama

- **Главная библиотека:** https://ollama.com/library — официальный каталог (на июнь 2026 — 4500+ моделей).
- **Поиск с фильтрами:** https://ollama.com/search — поле поиска + сортировка `popular` (по числу скачиваний) / `newest`.
- **Фильтр по возможностям** (тег `c`):
  - инструменты/function-calling — https://ollama.com/search?c=tools
  - зрение (vision) — https://ollama.com/search?c=vision
  - эмбеддинги — https://ollama.com/search?c=embedding

Как читать страницу модели (пример https://ollama.com/library/qwen3):

| Что смотреть | Зачем |
|---|---|
| Список тегов размеров (`qwen3:0.6b` … `:235b`) | у каждого указан **вес в ГБ** — это и есть ориентир по VRAM |
| Размер в ГБ рядом с тегом | если число ≥ вашей видеопамяти — часть уйдёт в RAM, скорость упадёт |
| Тег `:latest` | алиас, обычно средний размер (у qwen3 = 8b, 5.2 ГБ) |
| Дата обновления / pulls | свежесть и популярность |

Установка по тегу:

```
ollama run qwen3:8b
ollama pull qwen3:14b
```

Важно: на страницах библиотеки Ollama по умолчанию показаны **только размеры**, а не квантизации. Ollama по умолчанию отдаёт **Q4_K_M**. Полный список тегов (включая `q5_K_M`, `q8_0`, `fp16`) — на вкладке **Tags** модели, например https://ollama.com/library/qwen3/tags. Явный выбор квантизации:

```
ollama run qwen3:8b-q4_K_M
ollama run qwen3:14b-q8_0
```

### 2. HuggingFace — поиск GGUF

GGUF — это формат файла с весами под `llama.cpp`/Ollama/LM Studio: внутри и тензоры, и метаданные.

- **Все GGUF-модели:** https://huggingface.co/models?library=gguf
- **Самые востребованные сейчас:** https://huggingface.co/models?library=gguf&sort=trending
- **Документация по GGUF и таблица типов квантизации:** https://huggingface.co/docs/hub/gguf

Как искать и фильтровать:

1. На странице https://huggingface.co/models в левой панели — фильтр **Libraries → GGUF** и поле поиска по имени (`qwen3 gguf`, `gemma gguf`).
2. Сортировка справа: `Trending` / `Most downloads` / `Recently updated`.
3. Надёжные публикаторы готовых GGUF (имя в репозитории): **bartowski**, **unsloth**, **ggml-org**, а также официальные репо вендоров (например, https://huggingface.co/google/gemma-3-4b-it-qat-q4_0-gguf).

Чтение карточки модели (README репозитория):

- **Files and versions** — список `.gguf`-файлов. Имя файла = квантизация (`...Q4_K_M.gguf`, `...Q5_K_M.gguf`, `...Q8_0.gguf`), рядом — **размер в ГБ**.
- **Таблица квантизаций** в README у bartowski/unsloth: колонки «quant / размер / рекомендация». Берите строку, чей размер на 1–2 ГБ меньше вашей VRAM.
- **GGUF-вьюер метаданных** прямо на странице файла (показывает архитектуру, контекст, тип тензоров).
- Раздел **License** и **Model card** — лицензия, размер контекста, базовая модель, язык.

Запуск GGUF с HuggingFace в Ollama — без ручного скачивания:

```
ollama run hf.co/bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M
```

### 3. Что такое квантизация

Квантизация — сжатие весов с FP16 (16 бит) до 8/5/4/3/2 бит. Меньше бит → меньше файл и VRAM, медленнее растёт потеря качества.

Расшифровка `Q4_K_M`:

- **Q4** — 4 бита на вес.
- **_K** — «K-quant», умное поблочное квантование (точнее старых `Q4_0`/`Q4_1`).
- **_M** — размер варианта: **S** (small) / **M** (medium) / **L** (large). При одном уровне `_M` точнее `_S`.

Ориентир по уровням:

| Квант | Бит/вес | Качество | Когда |
|---|---|---|---|
| Q8_0 | ~8.5 | почти как оригинал | если VRAM хватает |
| Q6_K | ~6.6 | отличное | запас по памяти |
| Q5_K_M | ~5.5 | очень хорошее | компромисс |
| **Q4_K_M** | ~4.5 | хорошее, **дефолтный выбор** | стандарт на 8 ГБ |
| Q3_K | ~3.4 | заметная просадка | только если иначе не влезает |
| Q2_K | ~2.6 | сильная деградация | крайний случай |

Правило: **не опускайтесь ниже Q4_K_M**, если цель — рабочее качество (код, рассуждения).

### 4. Подбор размера модели под VRAM

Оценка веса в Q4_K_M: **≈ 0,55–0,65 ГБ на 1 млрд параметров**, плюс **1–2 ГБ** на KV-кэш и контекст.

| Параметры | Вес Q4_K_M | + контекст (итого) | Минимум VRAM |
|---|---|---|---|
| 3–4B | ~2–2,5 ГБ | ~3–4 ГБ | 6 ГБ |
| **7–8B** | ~4,5–5 ГБ | **~6–7 ГБ** | **8 ГБ** |
| 14B | ~8–9 ГБ | ~10–11 ГБ | 12–16 ГБ |
| 30–32B | ~18–20 ГБ | ~22–24 ГБ | 24 ГБ |
| 70B | ~40 ГБ | ~45 ГБ | 2×24 ГБ или 48 ГБ |

Для вашей **RTX 3070 Ti (8 ГБ)**:

- Целевой класс — **7–8B в Q4_K_M** (Qwen3 8B, Gemma 3 12B уже впритык, Phi-4 mini): полностью помещаются в VRAM, 40–60 ток/с.
- 14B физически запустится, но частично уйдёт в системную RAM (offload) → скорость резко падает; для чувствительной работы не рекомендуется.
- Чтобы оставить место под контекст: для 8 ГБ держите вес файла **до ~5,5 ГБ** и контекст 4–8K.
- Проверка фактической раскладки GPU/CPU после загрузки:

```
ollama ps
```

Если в выводе есть доля `CPU` — модель не влезла целиком; берите меньший размер или квант ниже.

### Как грамотно формулировать запрос

1. **Ищите по тексту ошибки дословно, на английском.**
   - Скопируйте ключевую строку ошибки целиком, без своих переменных (имён файлов, путей, ID).
   - Оберните в кавычки для точного совпадения: `"CUDA out of memory"`.
   - Пример плохо: `почему оллама не запускается видеокарта`.
   - Пример хорошо: `ollama "CUDA error" out of memory RTX 3070`.

2. **Формула запроса:** `[инструмент] + [ключевая фраза ошибки в кавычках] + [ваше железо/контекст]`.
   - `ollama docker "no compatible GPUs were discovered"`
   - `open-webui "connection refused" ollama localhost`

3. **Убирайте «свои» детали из запроса.** Путь `E:\dev\models\my-model.gguf` уникален и сломает поиск. Оставьте только то, что общее для всех: `model.gguf failed to load`.

4. **Сужайте сайтом, когда нужно:** добавьте `site:github.com` или `site:reddit.com` в Google.

### Поиск на английском для русскоязычного

- **Английский — обязателен.** 95% решений по локальным LLM написаны по-английски. Русскоязычных тредов мало и они устаревают.
- **Не переводите ошибку.** Текст ошибки вставляйте как есть (он и так на английском). Переводить нужно только ваше *описание* проблемы.
- **Используйте переводчик как помощника, не как костыль:** [DeepL](https://www.deepl.com/translator) точнее Google Translate для технических текстов. Схема: написали вопрос по-русски → перевели в DeepL → выложили английский вариант.
- **Минимальный технический словарь для запросов:**

  | Русский | Английский (для поиска) |
  |---|---|
  | не запускается / падает | crashes / fails to start |
  | не хватает памяти | out of memory (OOM) |
  | зависает | hangs / freezes |
  | как настроить | how to configure / how to set up |
  | не видит видеокарту | GPU not detected / not using GPU |
  | медленно работает | slow inference / low performance |
  | ошибка при загрузке модели | failed to load model |

- **Читать английский проще, чем писать.** Для чтения хватит и браузерного перевода страницы; для *запроса* — пишите по-английски, это критично для попадания в выдачу.

### Как читать и искать в GitHub Issues

GitHub Issues — это база уже решённых проблем. Главное — уметь её фильтровать. [Документация по синтаксису поиска](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests).

1. **Ищите внутри репозитория, включая закрытые.** Решение чаще лежит в *закрытых* (Closed) issue.
   - В строке поиска issue репозитория: `is:issue "out of memory" RTX` (по умолчанию ищет и открытые, и закрытые при явном запросе).
   - Только закрытые (где есть готовое решение): `is:issue is:closed "out of memory"`.

2. **Полезные квалификаторы поиска:**

   | Квалификатор | Что делает | Пример |
   |---|---|---|
   | `is:issue` / `is:pr` | Только issue или только pull request | `is:issue gpu` |
   | `is:open` / `is:closed` | Открытые / закрытые | `is:closed cuda` |
   | `in:title` | Искать только в заголовке (меньше шума) | `out of memory in:title` |
   | `label:bug` | По метке | `label:bug docker` |
   | `sort:comments-desc` | Сначала самые обсуждаемые (часто = самые важные) | `cuda sort:comments-desc` |
   | `"..."` | Точная фраза | `"failed to load model"` |
   | `-` (минус) | Исключить слово | `cuda -windows` |

3. **Как читать тред issue:**
   - Прочитайте *первое* сообщение — описание проблемы (совпадает ли с вашей).
   - Прыгайте к **концу** треда: решение и итог обычно там.
   - Ищите комментарий с реакцией 👍 или отмеченный мейнтейнером — обычно это рабочий ответ.
   - Если issue закрыт ссылкой на PR (pull request) — решение в коде этого PR.

4. **Если не нашли — создавайте свой issue правильно:** что сделали → что ожидали → что получилось (полный текст ошибки) → версии (`ollama --version`, ОС, GPU, объём VRAM) → шаги воспроизведения. Чем точнее, тем быстрее ответят.

### Поиск кода на GitHub

Когда нужно не «как починить», а «как этим пользоваться» — смотрите реальный код других. [Синтаксис Code Search](https://docs.github.com/en/search-github/github-code-search/understanding-github-code-search-syntax).

- **Фильтры:** `language:python`, `repo:ollama/ollama`, `path:*.yaml`.
- **Пример:** найти примеры docker-compose для Open WebUI с GPU — `open-webui language:yaml "deploy" "gpus"`.
- **Пример:** как зовут параметр в API Ollama — `repo:ollama/ollama language:go "num_gpu"`.
- Регулярные выражения — в слэшах: `/num_ctx\s*=/`.

## Как самому диагностировать и решать проблемы

Цель раздела — дать воспроизводимый алгоритм, чтобы вы выходили из любой технической проблемы сами, без ассистента. Принцип один: **проблему не угадывают, её локализуют** — сужают зону поиска, пока не останется одна причина.

### Методология: 7 шагов

| # | Шаг | Что делать | Зачем |
|---|-----|------------|-------|
| 1 | Читать логи | Найти точное сообщение об ошибке и стектрейс в логах сервиса, а не описывать симптом «не работает» | 80% ответа уже лежит в логе; симптом обманчив, лог — факт |
| 2 | Минимальный воспроизводимый пример (MRE) | Свести проблему к наименьшему набору кода/конфигурации, который всё ещё её даёт | Отсекает лишнее; часто причина находится в процессе сведения |
| 3 | Искать ошибку дословно | Копировать текст ошибки целиком (без своих путей/ID) в поиск, в кавычках | Чужие пути и хэши «загрязняют» запрос и прячут релевантные ответы |
| 4 | Читать GitHub issues | Искать ошибку в трекере конкретного инструмента, открытые и закрытые | Баг инструмента уже описан другими; в issue — обходные пути и версии-фиксы |
| 5 | Бисекция (`git bisect`) | Если «вчера работало» — бинарным поиском найти коммит, сломавший сборку | Превращает «где-то в 200 коммитах» в `log₂(200) ≈ 8` проверок |
| 6 | Проверка гипотез по одной | Менять ровно один параметр за итерацию, фиксировать результат | Два изменения сразу — и вы не знаете, какое подействовало |
| 7 | Откат изменений | Не помогло — вернуть как было (`git stash`, `git restore`), и только потом следующая гипотеза | Не накапливать «грязь» из неудачных попыток, иначе сломается ещё и она |

Правила, которые экономят часы:

- **Сначала прочитать ошибку до конца.** Реальная причина часто в первой строке стектрейса или в `Caused by:`, а не в последней.
- **Запрос в поиск без личного.** Уберите `C:\Users\PizZzA\...`, GUID, порты — оставьте инвариантную часть текста ошибки.
- **Менять одно — фиксировать всё.** Ведите простой журнал: гипотеза → действие → результат. Без журнала на 5-й итерации вы повторяете 2-ю.
- **Откат — это норма, а не поражение.** Чистое состояние между гипотезами обязательно.

### MRE: как сводить к минимуму

По методике Stack Overflow ([help/minimal-reproducible-example](https://stackoverflow.com/help/minimal-reproducible-example)):

1. **Минимальный** — убрать весь код, без которого проблема всё ещё воспроизводится.
2. **Полный** — то, что осталось, должно запускаться у другого человека без догадок.
3. **Воспроизводимый** — перед тем как спрашивать, проверить, что урезанный пример реально даёт ту же ошибку.
4. Текст ошибки и номер строки — копировать, а не пересказывать.

Побочный эффект: пока вы вырезаете лишнее, причина находится сама примерно в половине случаев.

### Бисекция: `git bisect`

Когда «работало день назад, сейчас нет», а коммитов много — не читайте их подряд. Бинарный поиск по официальной документации ([git-scm.com/docs/git-bisect](https://git-scm.com/docs/git-bisect)):

```powershell
git bisect start
git bisect bad                 # текущий коммит — сломан
git bisect good <хэш-или-тег>  # коммит, где точно работало
# git checkout-ит середину — вы проверяете и помечаете:
git bisect good                # на этом коммите всё ок
git bisect bad                 # на этом уже сломано
# ...повторять, пока не назовёт первый «плохой» коммит
git bisect reset               # выйти из режима
```

Автоматизация — если проверку можно выразить скриптом (exit 0 = good, ≠0 = bad):

```powershell
git bisect run npm test
```

`git bisect` сам прогонит скрипт на каждом шаге и сойдётся к виновному коммиту без ручных пометок.

### Разбор реального примера: «Docker Desktop не стартует на Windows»

Типичная ваша конфигурация: Windows 11, Docker Desktop на WSL2-бэкенде, GPU RTX 3070 Ti. Идём строго по гипотезам, от самой вероятной.

#### Гипотеза 1 — отключён гипервизор (самая частая причина)

Docker Desktop на WSL2 требует включённого аппаратного гипервизора. Стороннее ПО (антивирусы, VirtualBox, VMware, игровые анти-читы) иногда выключает `hypervisorlaunchtype` при старте системы.

Проверка — **PowerShell от администратора**:

```powershell
bcdedit /enum | Select-String -Pattern "hypervisorlaunchtype"
```

- Видите `hypervisorlaunchtype  Off` → гипервизор отключён, это и есть причина.
- Чинится одной командой и перезагрузкой:

```powershell
bcdedit /set hypervisorlaunchtype Auto
Restart-Computer
```

Параллельно убедитесь, что **виртуализация включена в BIOS/UEFI** (Intel VT-x / AMD-V / SVM). Быстрая проверка — в Диспетчере задач → Производительность → ЦП → строка «Виртуализация: Включено». WSL2 без неё не запустится в принципе.

#### Гипотеза 2 — не установлены/не обновлены компоненты WSL2

WSL2 использует подсистему Hyper-V через optional-компонент «Virtual Machine Platform» (доступен на всех редакциях, включая Home — полноценный Hyper-V для этого не нужен).

Проверка состояния:

```powershell
wsl --status
wsl --version
```

Включить компоненты (PowerShell от администратора), если отсутствуют:

```powershell
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
wsl --update
Restart-Computer
```

> Известная регрессия: на сборках Windows 11 25H2 (Build 26200.x), особенно в редакциях Home / Single Language, встречаются проблемы совместимости WSL/Docker. Лечится накатом всех обновлений Windows и `wsl --update`. Подтверждение — обсуждение на [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5759687/wsl-docker-and-edition-windows-11-home-single-lang).

#### Гипотеза 3 — читаем логи Docker (если 1 и 2 в порядке)

Логи Docker Desktop на Windows ([официальная страница troubleshoot](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/)):

```powershell
# открыть каталог логов
explorer $Env:LOCALAPPDATA\Docker\log
```

- `%LOCALAPPDATA%\Docker\log\host\` — логи UI/бэкенда (`electron-*.log`); ищите здесь строки уровня `error`/`fatal` на момент запуска.
- `%LOCALAPPDATA%\Docker\log\vm\` — логи демона внутри ВМ (с версии Docker Desktop 4.9.0).

Машинная диагностика встроенным инструментом:

```powershell
& "C:\Program Files\Docker\Docker\resources\com.docker.diagnose.exe" check
```

(для per-user установки путь: `%LOCALAPPDATA%\Programs\DockerDesktop\resources\com.docker.diagnose.exe`). Инструмент сам прогоняет набор проверок и помечает провалившиеся.

Системные ошибки времени запуска — через журнал событий Windows ([Get-WinEvent на Microsoft Learn](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent)):

```powershell
Get-WinEvent -FilterHashtable @{ LogName='Application'; Level=2; StartTime=(Get-Date).AddHours(-1) } |
  Select-Object TimeCreated, ProviderName, Message | Format-List
```

`Level=2` — только ошибки; запускать тоже от администратора, иначе часть журналов недоступна.

#### Гипотеза 4 — прокси / TLS-перехват (если в логах ошибки сети или образы не тянутся)

Симптом: Docker стартует, но `docker pull` падает с ошибкой TLS / `x509: certificate signed by unknown authority` / таймаутом до `registry.docker.io`. Характерно для корпоративных сетей и VPN с SSL-инспекцией.

Где смотреть и править ([гайд по сертификатам](https://docs.docker.com/engine/security/certificates/)):

1. **Настройки прокси Docker Desktop** — Settings → Resources → Proxies → Manual proxy configuration. Хранятся в:
   ```
   %APPDATA%\Docker\http_proxy.json
   ```
2. **TLS-сертификат перехватывающего прокси** — если корпоративный прокси подменяет сертификаты, его корневой CA нужно сделать доверенным. Для конкретного реестра — положить `*.crt` в каталог с именем хоста реестра:
   ```
   /etc/docker/certs.d/registry.docker.io/ca.crt
   ```
   (внутри WSL/демона), либо добавить CA в доверенные на уровне Windows.
3. Быстрый тест гипотезы — **временно отключить прокси/VPN** и повторить `docker pull hello-world`. Заработало → причина в прокси/TLS, чините по пунктам 1–2. Не заработало → откатываете изменение и идёте к следующей гипотезе.

#### Итог разбора

Порядок гипотез выбран по убыванию вероятности и возрастанию трудозатрат: гипервизор и виртуализация (1 команда) → компоненты WSL2 → чтение логов → сеть/TLS. На каждом шаге меняется ровно один фактор, и если он не помог — откат перед следующим. Это и есть локализация: вы не «чините Docker наугад», а последовательно вычёркиваете причины, пока не останется одна.

## Цифровой двойник: дообучение на своём стиле

Цель этапа: взять базовую открытую модель и адаптером научить её писать в вашей манере — лексика, длина фраз, эмодзи, типичные ответы. Полное переобучение модели не нужно и невозможно на 8 ГБ; используется **QLoRA** — обучается лёгкий адаптер (десятки МБ) поверх замороженной 4-битной модели.

### 1. Выбор инструмента

| Инструмент | Для кого | Плюсы | Минусы | Подходит ли под 8 ГБ |
|---|---|---|---|---|
| **WeClone** | Ваша задача «из коробки» | Готовый конвейер: экспорт Telegram → датасет пар → обучение → деплой; чистит ПДн (Presidio) | Молодой проект, быстро меняется; под капотом тот же LLaMA-Factory | Да, через QLoRA, но 7B в 16-бит просит ~16 ГБ — берите 4-бит/3–4B |
| **Unsloth** | Кто хочет понять механику и уложиться в 8 ГБ | До −70% VRAM и ~2× скорость; готовые Colab-ноутбуки; прямой экспорт в GGUF | Ручная подготовка датасета | Да, это лучший вариант для 8 ГБ |
| **LLaMA-Factory** | Новичок, не любящий код | Веб-интерфейс LlamaBoard, zero-config, огромное сообщество (~70k звёзд) | Тяжелее, чем Unsloth по VRAM | С QLoRA — да |
| **Axolotl** | Продвинутый, любит YAML | Гибкость, воспроизводимость, production | Нет GUI, крутая кривая входа | Да, но избыточен для старта |

Рекомендация под ваш профиль (соло, RTX 3070 Ti 8 ГБ, цель — двойник из Telegram):

1. **Хотите результат быстро и по теме** — начните с **WeClone**: он закрывает весь путь от экспорта Telegram до бота.
2. **Хотите понять, как это работает, и гарантированно влезть в 8 ГБ** — возьмите **Unsloth** (учит подготовке данных и QLoRA вручную, это полезный навык).
3. **LLaMA-Factory** держите как запасной no-code вариант (веб-UI), **Axolotl** — на потом, когда понадобится тонкий контроль.

### 2. Подготовка данных из Telegram (пары «контекст → ответ»)

Экспорт:

1. Telegram Desktop → нужный чат → меню (три точки) → **Export chat history**.
2. Формат — **JSON** (не HTML), медиа можно отключить, если нужен только текст. Получите `result.json`.

Формат обучающих пар. Дообучение на стиле — это supervised fine-tuning, где модель учится выдавать **ваш** ответ на предшествующий контекст. Один пример = реплики собеседника (контекст) + ваша реплика (целевой ответ):

```json
{
  "messages": [
    {"role": "user", "content": "Реплики собеседника (последние N сообщений диалога)"},
    {"role": "assistant", "content": "Ваш реальный ответ из переписки"}
  ]
}
```

Правила сборки датасета (критично для качества двойника):

- **Целевой ответ — всегда ваш**; контекст — сообщения других участников (плюс, опционально, ваши предыдущие реплики для связности).
- **Склеивайте серии**: подряд идущие сообщения одного автора объединяйте в одну реплику.
- **Фильтруйте мусор**: пересланные сообщения, стикеры без текста, голосовые, очень короткие «ок»/«ага» (либо оставьте, если это часть вашего стиля).
- **Удалите ПДн и приватное**: телефоны, адреса, пароли, чужие тайны. WeClone делает это автоматически через Microsoft Presidio (`weclone-cli make-dataset`); при ручной сборке вычищайте регулярками.
- **Объём**: для уловимого стиля достаточно нескольких тысяч качественных пар; больше — лучше, но чистота важнее количества.

В WeClone весь этот шаг — одна команда:

```
weclone-cli make-dataset
```

### 3. QLoRA на скромной VRAM (8 ГБ)

Ключевые настройки, которые удерживают обучение в 8 ГБ:

- **Базовая модель**: берите 3–4B класса (например, Qwen или Llama-3.x 3B) или 7–8B строго в 4-бит. Чем меньше модель, тем больше запас по VRAM и контексту.
- **`load_in_4bit=True`** — 4-битная квантизация NF4 (это и есть «Q» в QLoRA).
- **LoRA-ранг** r = 8–16, `lora_alpha` = 16–32 — для имитации стиля высокий ранг не нужен.
- **`max_seq_length`** 1024–2048 — диалоги короткие, не раздувайте.
- **batch size = 1–2** + **gradient accumulation** 4–8 для эффективного батча.
- **Gradient checkpointing** включён (в Unsloth — `use_gradient_checkpointing="unsloth"`).
- 1–3 эпохи; следите, чтобы loss не упал слишком низко (переобучение → модель дословно повторяет переписку).

Скелет на Unsloth:

```python
from unsloth import FastLanguageModel
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen2.5-3B-Instruct",
    max_seq_length=2048, load_in_4bit=True,
)
model = FastLanguageModel.get_peft_model(
    model, r=16, lora_alpha=16,
    use_gradient_checkpointing="unsloth",
)
# далее SFTTrainer на вашем JSONL с парами messages
```

В WeClone обучение запускается одной командой:

```
weclone-cli train-sft
```

### 4. Экспорт в GGUF и импорт в Ollama

GGUF — формат, который понимает Ollama. Два пути:

Путь A — слить адаптер в модель и экспортировать в GGUF (проще для Ollama):

```python
# Unsloth: сохранить уже квантованный GGUF
model.save_pretrained_gguf("twin-model", tokenizer, quantization_method="q4_k_m")
```

Затем создайте `Modelfile`:

```
FROM ./twin-model/unsloth.Q4_K_M.gguf

SYSTEM "Ты отвечаешь в стиле автора переписки: коротко, живо, как в личных сообщениях."
PARAMETER temperature 0.8
```

И зарегистрируйте модель:

```
ollama create twin -f Modelfile
ollama run twin
```

Путь B — отдельный LoRA-адаптер через инструкцию **ADAPTER** (без слияния):

```
FROM qwen2.5:3b
ADAPTER ./twin-lora.gguf
```

Важные ограничения `ADAPTER` (из официальной документации Ollama):

- Базовая модель в `FROM` **должна совпадать** с той, на которой обучался адаптер, иначе поведение будет хаотичным.
- Путь к адаптеру — абсолютный или относительно `Modelfile`.
- Поддержка адаптеров ограничена семействами Llama, Mistral/Mixtral, Gemma. Для надёжности с другими моделями (например, Qwen) выбирайте **путь A** (слияние в GGUF).

Для новичка путь A надёжнее: меньше нюансов совместимости.

### 5. Без своего GPU — бесплатный Google Colab

Если 8 ГБ не хватает или хотите не нагружать машину:

- **Google Colab** даёт бесплатный GPU **Tesla T4 (16 ГБ)** — этого хватает на QLoRA моделей до ~22B через Unsloth.
- Unsloth публикует готовые ноутбуки «Run all»: подставляете свой датасет, жмёте запуск, на выходе — GGUF, который скачиваете и подключаете к локальной Ollama по инструкции из пункта 4.
- Бесплатный тариф ограничивает время сессии и может отключать GPU при простое — сохраняйте чекпоинты на Google Drive.
- Альтернатива с тем же T4 — **Kaggle Notebooks** (около 30 часов GPU в неделю).

Рабочий сценарий «без своего железа»: данные готовите локально → обучение в Colab на T4 → GGUF забираете на свой ПК → инференс двойника локально в Ollama.

## Как расти как разработчик (самообучение)

### Принцип: учиться через проекты, а не через туториалы

Просмотр курсов создаёт иллюзию прогресса («tutorial hell»). Навык появляется только когда вы пишете код сами и упираетесь в проблемы. Рабочий цикл:

1. Берёте минимальную фичу или проект чуть выше текущего уровня.
2. Пишете сами до первого затыка.
3. Гуглите / читаете доки / спрашиваете ИИ — но только по конкретному затыку, не «как сделать всё».
4. Доводите до рабочего состояния, рефакторите, выкладываете на GitHub.
5. Повторяете с чуть более сложной задачей.

Проекты для портфолио (ориентир на Vue/TS): SPA с роутингом и стейтом (Pinia), приложение с реальным API и обработкой ошибок/загрузки, компонентная библиотека на TS-дженериках, full-stack с бэком (Node/Nest). Для работы за рубежом важнее 2–3 завершённых, отполированных проекта с README и живым демо, чем 20 заброшенных.

### Как читать документацию (это отдельный навык)

- **Сначала Getting Started / Quick Start целиком**, без копипасты. Цель — увидеть, как устроен инструмент, а не получить готовый код.
- **Изучайте API reference как карту, а не как книгу**: запомните, какие разделы есть и где их искать, а не содержимое наизусть.
- **Гуглите так: `site:vuejs.org composition api`** или `mdn fetch error handling` — это режет SEO-мусор и ведёт в первоисточник.
- **При ошибке** — читайте текст ошибки целиком и идите в раздел доки по упомянутому методу/опции, прежде чем гуглить дословно.
- **Сверяйте версию**: для Vue убедитесь, что это Vue 3 и Composition API, а не устаревший Vue 2 / Options API (много старых статей).
- **Читайте changelog и release notes** ключевых инструментов — это держит вас в курсе (например, Vapor Mode в Vue, Vite+ — направления 2026).

### Как использовать ИИ как наставника, а не как костыль

Граница простая: **ИИ объясняет и проверяет ваше мышление — но решение придумываете вы.** Локальная модель (Ollama) для приватных вопросов и работы офлайн; облачная — для сложных рассуждений и ревью.

**Делайте (рост):**

- «Объясни, почему этот код работает / в чём разница между X и Y» — за объяснением.
- «Вот моё решение: где слабые места, какие edge cases я упустил?» — за ревью уже написанного вами кода.
- «Дай 3 подхода к этой задаче с плюсами/минусами, но не пиши код» — за вариантами проектирования.
- «Задавай мне наводящие вопросы, пока я сам не приду к решению» — режим сократического наставника.
- «Сгенерируй упражнения по TS-дженерикам моего уровня с возрастающей сложностью» — за тренажёром.

**Избегайте (атрофия навыка):**

- «Напиши мне этот компонент целиком» и вставка без понимания.
- Принятие ответа без проверки — модели уверенно ошибаются (галлюцинации API, устаревший синтаксис). Всегда сверяйте с официальной документацией.
- Делегирование архитектурных решений на ранних задачах — именно их и нужно учиться принимать.

**Правило проверки:** прежде чем взять код от ИИ, добейтесь, что можете объяснить каждую строку и переписать без подсказки. Если не можете — это не ваш навык, а заёмный.

**Для «цифрового двойника»** (дообучение на переписках) тот же принцип: пройдите fine-tuning / LoRA сами по официальным гайдам Ollama и выбранного фреймворка, а ИИ используйте для объяснения параметров и диагностики ошибок обучения, а не для готового скрипта вслепую.

### Дисциплина роста

- **Учите по необходимости проекта (just-in-time), а не «на всякий случай».** Знание без применения забывается.
- **Code review своего старого кода раз в пару месяцев** — лучший индикатор прогресса.
- **Читайте чужой качественный код**: исходники Vue/Pinia на GitHub, разбор PR в open source.
- **Для работы за рубежом** дополнительно прокачивайте: технический английский (читать доки и писать в issues уже даёт его), Git/GitHub-гигиену (внятные коммиты, PR, README на английском), основы тестирования (Vitest) и алгоритмов для интервью.

## Маршрут: с чего начать

Пошаговый план под ваши цели. Каждый этап — законченный результат, который можно пощупать. Не перепрыгивайте: следующий этап опирается на навыки предыдущего.

### Неделя 1 — поднять локальную ИИ и убедиться, что GPU работает

Цель: рабочий чат с локальной моделью на вашей RTX 3070 Ti.

1. Установить Docker Desktop на WSL2-бэкенде — [инструкция](https://docs.docker.com/desktop/setup/install/windows-install/). Сразу проверить GPU в контейнерах — [GPU support](https://docs.docker.com/desktop/features/gpu/).
2. Поднять стек Ollama + Open WebUI одной командой через Docker — [Open WebUI Quick Start](https://docs.openwebui.com/getting-started/quick-start/).
3. Скачать первую модель целевого класса 7–8B Q4_K_M: `ollama run qwen3:8b` (Apache 2.0, влезает в 8 ГБ).
4. Проверить, что модель целиком на GPU: `ollama ps` — доли `CPU` быть не должно.
5. Контрольная точка: открыли веб-чат, задали вопрос, получили ответ на скорости 40–60 ток/с.

Если что-то не стартует — это не повод звать ассистента: пройдите раздел «Как самому диагностировать и решать проблемы», начиная с гипотезы про гипервизор.

### Неделя 2 — подключить локальную ИИ к IDE и писать код с ней

Цель: автодополнение и чат прямо в редакторе, на локальной модели.

1. Изучить OpenAI-совместимый API Ollama — [docs.ollama.com/openai](https://docs.ollama.com/openai): через него подключается большинство IDE-плагинов.
2. Поставить в редактор плагин с поддержкой локального бэкенда (Continue, Cline и аналоги), указать endpoint Ollama.
3. Для кода взять модель с тегом `tools` (function-calling) — [фильтр](https://ollama.com/search?c=tools); для автодополнения держать модель полегче, чтобы хватало VRAM.
4. Сразу выработать привычку из раздела «ИИ как наставник»: просить объяснения и ревью, а не готовые компоненты целиком.
5. Контрольная точка: написали небольшую фичу в реальном проекте, где ИИ объяснял и проверял, а решения принимали вы.

### Недели 3–4 — знания и RAG: своя база поверх локальной ИИ

Цель: модель отвечает по вашим документам/заметкам, а не только из общего знания.

1. Разобраться, что умеет Open WebUI из коробки: RAG, загрузка документов, tool calling — [главная документация](https://docs.openwebui.com/).
2. Подключить embedding-модель — [фильтр embedding](https://ollama.com/search?c=embedding) — и загрузить набор своих материалов (заметки, доки проекта).
3. Проверить ответы на цитируемость: модель должна ссылаться на ваши документы, а не выдумывать.
4. Контрольная точка: задаёте вопрос по своему материалу — получаете ответ с опорой на загруженные документы.

### Недели 5–7 — цифровой двойник: дообучение на своём стиле

Цель: модель, которая пишет в вашей манере. Это самый объёмный этап — заложите запас времени.

1. Выгрузить переписки из Telegram Desktop в **JSON** (`Export chat history`).
2. Выбрать путь по разделу «Цифровой двойник»: **WeClone** для быстрого результата «из коробки» либо **Unsloth**, если хотите понять механику и гарантированно уложиться в 8 ГБ.
3. Собрать датасет пар «контекст → ответ», вычистить ПДн (в WeClone — `weclone-cli make-dataset`).
4. Запустить QLoRA: локально на 3–4B/4-бит, либо обучение в Google Colab на бесплатном T4 (16 ГБ), если 8 ГБ мало.
5. Экспортировать в GGUF (путь A — слияние, надёжнее для новичка), собрать `Modelfile`, зарегистрировать: `ollama create twin -f Modelfile`.
6. Контрольная точка: `ollama run twin` отвечает узнаваемо в вашем стиле, без дословного повторения переписки (признак переобучения).

### Постоянно, фоном — рост как разработчик

Идёт параллельно всем этапам, не ждёт их завершения.

1. Взять **roadmap.sh** ([Vue](https://roadmap.sh/vue) / [TypeScript](https://roadmap.sh/typescript)) как карту и отметить пробелы.
2. Закрывать пробелы практикой на [The Odin Project](https://www.theodinproject.com/) / [freeCodeCamp](https://www.freecodecamp.org/), а конкретные вопросы — по [MDN](https://developer.mozilla.org/en-US/docs/Learn_web_development) и офиц. докам.
3. Довести 2–3 проекта до состояния портфолио: README, живое демо, чистые коммиты, английский в issues/PR.
4. Раз в пару месяцев — ревью своего старого кода как индикатор прогресса.

### Сквозной навык на всех этапах

На каждом этапе будут затыки — это норма. Не зовите ассистента первым делом: проблема почти всегда уже решена кем-то. Алгоритм один и тот же:

1. Прочитать ошибку до конца → 2. свести к MRE → 3. поискать дословно на английском (Google → GitHub Issues → r/LocalLLaMA) → 4. проверять гипотезы по одной с откатом.

Именно этот навык — «находить ответ самому» — и есть главная цель всего документа.
