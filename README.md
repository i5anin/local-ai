# 🦊 local-ai — локальная ИИ (Ollama + Open WebUI)

Изолированный стек локального ИИ в Docker: движок **Ollama** + веб-интерфейс
**Open WebUI** (чат, RAG по документам, веб-поиск). Работает на видеокарте,
данные не покидают машину.

Проверено на: Windows 11, Docker Desktop 4.56 (WSL2), **RTX 3070 Ti (8 ГБ)**.

---

## Требования

| Что | Зачем |
|---|---|
| **Docker Desktop** (бэкенд WSL2) | запуск контейнеров |
| **NVIDIA GPU + свежий драйвер** | инференс на видеокарте (иначе CPU, медленно) |
| **WSL2 + Virtual Machine Platform** | требует Docker; см. «Грабли запуска» |
| ~15 ГБ свободного диска | образы (~5 ГБ) + модели (~10 ГБ) |

---

## Быстрый старт

```powershell
cd E:\development\local-ai
docker compose up -d        # поднять контейнеры (первый раз тянет образы)
.\pull-models.ps1           # скачать модели (~9 ГБ)
```

Открыть:

- **Интерфейс:** http://localhost:3000 — при первом входе зарегистрируй
  локальный аккаунт (он станет админом; данные в локальной БД).
- **API Ollama:** http://localhost:11434 (для IDE-плагинов и скриптов).
- **Мониторинг:** http://localhost:19999 (Netdata — загрузка GPU, VRAM,
  температура; вход не нужен, «Skip and use the dashboard anonymously»).

После закачки: в интерфейсе сверху «Выберите модель» → нужная модель → чат.
Первый ответ грузит модель в VRAM (~10–20 c), дальше быстро.

## Модели (под 8 ГБ VRAM)

| Модель | Назначение | Размер |
|---|---|---|
| `qwen2.5-coder-ru` | написание кода | ~4.7 ГБ |
| `qwen2.5-ru` | общий чат | ~4.7 ГБ |
| `qwen3-vl-ru` | **изображения**: чертежи, сканы, скриншоты | ~3.3 ГБ |

Текстовые модели изображения не принимают — при попытке приложить картинку
интерфейс вернёт «model does not support multimodal requests». Для картинок
выбирать `qwen3-vl-ru`.

Это русскоязычные сборки базовых `qwen2.5-coder:7b` / `qwen2.5:7b`, собираются
скриптом `pull-models.ps1` из `shared/Modelfile.*`. Базовые теги после сборки
удаляются, чтобы их нельзя было выбрать в интерфейсе по ошибке (веса общие,
место не дублируется).

Зачем сборки: базовый Qwen на бытовые вопросы отвечает по-китайски и вставляет
английские слова в русский текст, а код-модель дополнительно склонна оборачивать
ответ в JSON вызова функции. В `Modelfile` это лечится системным промптом
(только русский, обычный текст) и низкой температурой (0.2–0.3) — на высокой
7B срывается на другой язык посреди фразы.

У `qwen3-vl-ru` дополнительно поднят контекст до 16384 (стандарт — 4096).
Это главный параметр качества на чертежах: при малом контексте изображение
сжимается сильнее и мелкий текст — размеры, допуски, основная надпись —
теряется первым. Цена: 5.5 ГБ VRAM под нагрузкой вместо 3.5, но модель
целиком остаётся в GPU.

Проверка на `ai_pf-forum/drawings/test-val.png`: обозначение, наименование,
материал с ГОСТ, масса, ⌀40h7, ⌀60js6, L=200, M12x1.25-6g, Ra 1.6/6.3,
закалка 45..50 HRC, покрытие — всё считано верно за 5 с. Базовый тег
`qwen3-vl:4b-instruct` не удаляется: на него ссылается проект `ai_pf-forum`.

Другую модель: `docker exec -it ollama ollama pull <модель>`.
14B-модели влезают, но впритык и медленно — повод для апгрейда VRAM
(цель 16 ГБ+, идеал — б/у RTX 3090 на 24 ГБ).

## Архитектура и изоляция

Контейнеры **не видят твою ОС**. Доступно только:

| Ресурс | Доступ |
|---|---|
| Папка `./shared` | ✅ читать/писать (единственное окно в файловую систему) |
| Интернет (исходящий) | ✅ есть (скачивание моделей, веб-поиск) |
| Видеокарта | ✅ проброшена в контейнер `ollama` |
| Остальная ФС (C:, E:\ …) | ❌ недоступна |
| Доступ к UI/API из локальной сети | ❌ порты только на `127.0.0.1` |

Модели и данные UI — в именованных Docker-томах (`ollama_models`,
`open_webui_data`), не в твоих папках.

## Команды

```powershell
docker compose ps                 # статус контейнеров
docker compose logs -f ollama     # логи движка (видно, нашёл ли GPU)
docker compose down               # остановить (данные в томах сохранятся)
docker compose pull               # обновить образы

docker exec -it ollama ollama list             # список моделей
docker exec -it ollama ollama ps               # что загружено в VRAM (GPU/CPU)
docker exec -it ollama ollama rm <модель>      # удалить модель
```

Проверить, что инференс идёт на GPU: `ollama ps` → колонка `PROCESSOR`
должна показывать `100% GPU`.

## Мониторинг загрузки GPU

Два инструмента, дополняющих друг друга:

| Инструмент | Что даёт |
|---|---|
| **Netdata** — http://localhost:19999 | графики и история: загрузка GPU, VRAM, температура, частоты, потребление, состояние контейнеров |
| **`.\gpu-watch.ps1`** | тот же срез в консоли и CSV-лог в `logs/`, плюс какая модель занимает VRAM и целиком ли она в GPU |

```powershell
.\gpu-watch.ps1 -Once                      # разовый снимок
.\gpu-watch.ps1 -IntervalSec 2 -Minutes 10 # наблюдение с логом
.\gpu-watch.ps1 -History 30                # пики за 30 мин из базы Netdata
```

Режим `-History` нужен потому, что `nvidia-smi` знает только «сейчас»: когда
модель выгружена и вентиляторы стихли, прошедшие пики остаются только в базе
Netdata.

### Как открыть графики в Netdata
1. На экране приветствия — ссылка **«Skip and use the dashboard anonymously»**
   мелким тусклым текстом внизу справа (не зелёная кнопка «Sign-in»: она ведёт
   на регистрацию в облаке и требует ключ агента).
2. Вкладка **Metrics** сверху.
3. В поле «Search charts» набрать `gpu` — отфильтруются 13 графиков видеокарты.

Шаг 1 повторяется при каждом открытии страницы: экран встроен в клиентскую
часть интерфейса, конфигурацией агента (`cloud.d/cloud.conf`, `[cloud]` в
`netdata.conf`) в версии 2.10 он не отключается — таких ключей там нет.
Если вход в облачную учётную запись уже выполнен, ссылка анонимного входа
исчезает: сначала «Sign out to switch user» внизу по центру.

⚠️ **Встроенный интерфейс Netdata отправляет данные наружу.** Он подключает
аналитику PostHog и ведёт запись сессии (в проверке — 643 КБ за одно открытие).
Переменная `DO_NOT_TRACK=1` глушит статистику самого агента, но не облачный
веб-интерфейс: он исполняется в браузере и обращается к своим адресам напрямую.
Метрики машины при этом никуда не уходят — но факт использования и действия в
интерфейсе уходят. Если это неприемлемо, пользоваться `gpu-watch.ps1` (только
локальный API) или блокировать домены аналитики на уровне браузера.

**Чего не покажет ни один из них** — сколько VRAM занимает конкретное
приложение. На Windows разбивку по процессам не отдаёт сама драйверная модель
(WDDM), поэтому `nvidia-smi` и всё, что на нём построено, показывает только
сумму. Кто именно занял память — смотреть в **Диспетчере задач** (вкладка
«Подробности», столбец «Выделенная память GPU»).

Это практически важно: браузер, Wallpaper Engine и мессенджеры суммарно
съедают около 2.5 ГБ из 8 ГБ, поэтому реально под модель остаётся ~5.5 ГБ.

Метрики CPU, ОЗУ и диска Netdata показывает **для виртуальной машины WSL2**
(она видит 12 ядер и ~11.6 ГБ ОЗУ), а не для Windows. Для хоста — Диспетчер
задач. Данные по видеокарте настоящие: она проброшена в контейнер.

## Веб-поиск и знания из документов

- **Веб-поиск** включён (DuckDuckGo, без ключа). В чате включи Web Search 🌐.
  Если не активен — Settings → Web Search.
- **RAG по своим файлам:** положи документы в `./shared` или загрузи в чате
  через `#` — модель будет отвечать с опорой на них.

## ⚠️ Грабли запуска (Windows + Docker Desktop)

Если Docker не стартует или модели не качаются — почти всегда одно из трёх:

### 1. Docker Desktop «failed to start», WSL2 не поднимается
Симптом: `HypervisorPresent: False` при включённой в BIOS виртуализации
(`VirtualizationFirmwareEnabled: True`); ошибка `HCS_E_HYPERV_NOT_INSTALLED`.
Гипервизор не запускается при загрузке. Фикс (PowerShell от админа):

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -All -NoRestart
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Windows-Subsystem-Linux -All -NoRestart
bcdedit /set hypervisorlaunchtype auto
```
**Затем перезагрузить ПК** (без ребута изменение не вступит в силу).

### 2. Краш «initializing Inference manager … dockerInference»
Падение Docker Model Runner на залипшем сокете. Нам он не нужен. Фикс —
в `%APPDATA%\Docker\settings-store.json`:

```json
"EnableDockerAI": false,
"EnableInference": false
```
Если сокет не удаляется (даже `fsutil`) — переименовать/удалить папку
`%LOCALAPPDATA%\Docker\run` (и `docker-secrets-engine`), Docker создаст заново.

### 3. `ollama pull` падает с EOF (registry.ollama.ai)
Причина: системный прокси/VPN (напр. `127.0.0.1:2080`) ломает TLS, а Docker
гонит через него трафик контейнеров. Прямой доступ к реестру при этом работает.
Фикс — в `settings-store.json` перевести прокси Docker в прямой режим
(системный прокси не трогаем):

```json
"ProxyHttpMode": "manual",
"OverrideProxyHttp": "",
"OverrideProxyHttps": "",
"OverrideProxyExclude": ""
```
Перезапустить Docker после правок настроек.

### 4. `docker compose up` падает: порт 11434 уже занят
Сообщение: «Only one usage of each socket address … 127.0.0.1:11434».
Причина: на хосте установлен **нативный Ollama для Windows**
(`%LOCALAPPDATA%\Programs\Ollama\ollama.exe`) и занимает тот же порт. В этом
стеке движок докерный — нативный нужно остановить:

```powershell
Get-Process ollama, 'ollama app' -ErrorAction SilentlyContinue | Stop-Process -Force
```
Чтобы не поднимался при входе в систему — убрать Ollama из автозапуска.
